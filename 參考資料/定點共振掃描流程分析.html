第一批股票系統如何從整個市場選出送去分析的那批股票？

掃描的第一步不是直接分析所有股票，而是先用兩道門檻快速從整個市場「切一刀」， 把幾千支股票縮減到最多 200 支，才送去做深度分析。以下是完整漏斗過程：

全市場 N 支
📡 Step A：取得整個市場的即時快照
調用 /api/market/snapshot?market=TWSE&sector=ALL，取回整個市場（或指定類股）今日所有股票的即時行情， 包含每支股票的：成交量（Trading_Volume）、昨收（prevClose）、今收（close）、漲跌（spread）等欄位。

✦ 全市場：包含該市場（上市或上櫃）的所有代號，約 900~1,000 支。
✦ 特定類股：指你在下拉選單選擇的「產業類型」，例如：半導體業、電腦週邊、電子零組件、航運業、生技醫療等。 每個類股的成分股數量不等，通常在 30~200 支之間。
✦ 資料來自 Redis 快取（TTL 1小時）或交易所 API 即時抓取
門檻一：排除無效股票
🔍 Step B：兩條件過濾（程式碼邏輯）
條件一：成交量 > 0（s.Trading_Volume > 0）
→ 排除今日完全沒有成交的股票（停牌、無人交易等），這類股不具備分析意義。

條件二：跌幅不低於 -0.1%（s.spread >= -0.1）
→ 排除今日已在大幅崩跌的股票。系統策略是「找爆發股」，崩跌股即使之後分析通過也不推薦進場。
💡 為什麼 -0.1 而不是 0？
給予極小幅度的容錯空間（-0.1 ≈ 幾乎持平），避免因計算誤差把「今日微跌 0.05%」的好股票也排除掉。
依成交量由大到小排序
最多 200 支
📊 Step C：依成交量排序，取前 200 支
過濾後剩餘的股票按今日成交量由大到小排序，然後用 .slice(0, 200) 只取前 200 支。

✦ 成交量越大 → 市場關注度越高 → 爆量信號越有意義
✦ 200 是「硬上限」，不是「固定值」——如果過濾後只剩 95 支，就只送 95 支去分析
✦ 如果你輸入了 4 位數字股票代號（如：2330），該股強制置頂排在第一位
送去深度分析（Phase 3）
🔬 Step D：五維深度分析 → 最終推薦
每支股票都走完完整的五維評分（量能30＋均線22＋法人22＋融資11＋營收15）， 同時必須同時滿足三大信號共振或綜合評分 ≥ 60 分， 且 MA5 > MA20（多頭排列），才會被標記為 is_recommended = true。
昨天 200 vs 今天 95為什麼候選數量每天不同？最後 3 支是怎麼篩出來的？

「200」只是程式設定的上限天花板，實際送去分析的數量取決於當天市場有多少股票通過 Step B 的兩條門檻。

✅ 昨天：通過 200 支（達到上限）
  • 市場整體氣氛較佳，大多數股票有成交量
  • 崩跌（spread < -0.1）的股票少
  • 快照中 的合格股 ≥ 200，取前200截斷
  • 結果：系統送了 200 支去深度分析
⚠️ 今天：只有 95 支（未達上限）
  • 市場整體偏弱，更多股票崩跌被過濾
  • 或選擇了特定類股，本身股票數量少
  • 或今日交投冷清，零成交股票增加
  • 結果：合格股只有 95 支，全部送去分析
常見原因一覽：
① 選擇了特定類股（非全市場）→ 該類股本身只有幾十支，過了條件後自然少
② 大盤弱勢日 → 大量股票跌幅超過 -0.1%，被門檻二排除
③ 非交易活躍時段 → 零成交股增加，被門檻一排除
④ Redis 快取是舊資料（TTL 1小時內未過期）→ 快照反映的是最近一次更新的行情，若市場變化快也可能有差異
三層漏斗95 支候選股如何最終縮減到 3 支推薦結果
95 支（今日候選stock pool）
第一層：市場快照 + 成交量/跌幅預篩
已通過「有成交量」＋「非崩跌（≥ -0.1%）」兩條門檻 → 95 支合格進入深度分析隊列
深度分析（五維評分）
假設通過評分：約 5~20 支
第二層：五維綜合評分 ≥ 60分 OR 三大信號全中
每支股票需抓取 60 天股價歷史、法人資料、月營收、融資數據，計算五維分數。
通過條件（AND 邏輯，需同時滿足）：
✦ （finalScore ≥ 0.6） 或 （V-Ratio ≥ 3.5x 且 MA Gap ≤ 2% 且 今日漲幅 ≥ 3%）
✦ MA5 > MA20（多頭排列，兩者均需成立才能 is_recommended = true）

這一層是最嚴格的淘汰關卡，通常只有 5~30% 的候選股能通過
前端附加爆發潛力分排序
最終 3 支（顯示結果）
第三層：爆發潛力分排名（前端排序）
通過第二層的股票，前端再計算「爆發潛力分」（volScore + priceScore + squeezeScore）， 由高到低排列，全部顯示（不限數量）。

✦ 今天顯示 3 支，代表只有 3 支同時滿足：五維評分門檻 + 多頭排列
✦ 不是「只取前3」，而是「只有3支通過了所有條件」
✦ 若全市場氣氛強勁，可能找到 10~20 支；若氣氛弱，可能 0 支
📌 總結：為什麼結果股數每天都不一樣？
因為整個系統沒有「強制取 N 支」的邏輯——每一層都是條件過濾，不是「取樣」。 結果數量完全由當天市場的技術指標狀態決定：
· 大盤強勢、成交量放大 → 通過門檻的股票多 → 結果多
· 大盤弱勢、量縮震盪 → 符合「量能激增 + 均線糾結 + 技術突破」的股票少 → 結果少甚至為 0
· 這正是系統設計的核心哲學：「寧缺毋濫，只顯示真正共振的標的」
STEP BY STEP完整執行步驟文字說明
  1. 使用者觸發：點擊按鈕，onClick={() => runScan()} 觸發；執行期間按鈕禁用。
  2. 前端狀態重置：setStage('fetching')，清空舊結果/錯誤/旗標，記錄計時起點 t0。
  3. 呼叫快照 API：GET /api/market/snapshot?market=&sector=。Redis 快取鍵 tsbs:snap:v2:{market}:{sector}（TTL 1h）；未命中則呼叫交易所 API 並回寫 Redis。
  4. 前端候選預篩：setStage('filtering')，過濾量能 > 0 且跌幅 > -0.1%，依成交量排序取前 200 支。4 位數字搜尋詞時目標股強制置頂。
  5. 批次送出分析：setStage('analyzing')，每 25 支一批次迴圈呼叫 POST /api/scan/analyze，同步更新進度條。
  6. 後端產業對應預取：analyze/route.ts 一次性取得整批次的產業對應表，避免重複呼叫。
  7. 並發個股分析：每批 25 支再分 15 支一組 Promise.allSettled 並發，呼叫 ScannerService.analyzeStock()。
  8. 四項資料抓取（均先查 Redis）：① 60天股價歷史（FinMind → Exchange備援，TTL 4h）② 10天法人買賣超（TTL 4h）③ 400天月營收（TTL 12h）④ 10天融資融券（TTL 4h）。
  9. 技術指標計算（engine.ts / evaluateStock()）：計算 V-Ratio（當日量 ÷ 前45日均量）、MA5/MA20 糾結度（|MA5-MA20|÷MA20）、今日突破幅度、多/空頭排列。
  10. 五維綜合評分：量能(30) + 均線(22) + 籌碼/法人(22) + 融資軋空(11) + 月營收(15) = 最高 100 分，轉換為 0~1 的 finalScore。多頭排列均線分 ×1.2，空頭排列 ×0.5。
  11. 推薦標記：is_recommended = (finalScore ≥ 0.6 OR 三大信號全中) AND MA5 > MA20。
  12. 前端爆發潛力分疊加：額外計算 volScore + priceScore + squeezeScore，作為最終排序依據。
  13. 最終過濾 + 排序：只保留 is_recommended=true 或搜尋命中的股票，依 potential_score 由高到低排序。
  14. 結果顯示 + 歷史儲存：有結果時顯示 StockCard，同時儲存掃描 Session 至 localStorage.tsbs_scan_history（最多 50 筆）。
  15. 完成狀態：setStage('complete') → 3 秒後 idle，按鈕恢復，Footer 顯示耗時統計。
三大信號共振成立條件（預設閾值）
❶ 量能激增 V-Ratio ≥ 3.5x（當日量 ÷ 前45日均量） ❷ 均線糾結 MA Gap < 2%（|MA5-MA20| ÷ MA20） ❸ 技術突破 今日漲幅 ≥ 3% 且收盤 > max(MA5, MA20) 加分：MA5 > MA20（多頭排列）
三個閾值均可在「信號閾值配置」面板調整（量能 1~6x、MA 0.5~5%、突破 1~8%）。

效能設計快取與效能優化機制
  1. Redis 多層快取：快照、股價歷史、法人資料、月營收、融資資料均有獨立快取 Key 與 TTL，大幅降低對外部 API 重複呼叫。
  2. Session Storage（瀏覽器端）：頁面初始化時快取產業對應表與快照，避免重新整理後重複抓取。
  3. 批次分析（每批 25 支）：前端每批送 25 支，後端內部再 15 支並發，兼顧吞吐量與避免504/502超時。
  4. 候選上限 200 支：快照通常數百~千支，預先過濾至 200 支，分析時間縮短約3倍。
  5. Promise.allSettled：單支分析失敗不影響整批，確保盡可能多的結果被收集。
